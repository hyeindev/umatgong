# 우맛공 (Umatgong) — 서비스 기획서

> 우리들의 맛집 공유
> v0.2 · 2026-09-29

---

## 1. 한 문장

**친구들끼리만 보는 맛집 지도.** 찍어둔 음식 사진이 자동으로 지도에 꽂히고,
나중에 그 근처에 가면 친구가 검증한 곳이 뜬다.

---

## 2. 문제

**믿을 만한 맛집 정보가 없다.** 포털 리뷰는 광고와 체험단이 섞여 신뢰를 잃었다.
결국 "친구가 맛있다고 한 곳"으로 돌아가지만, 그 정보는 카톡 대화 속에 흘러가 버린다.

**기록은 남지만 활용되지 않는다.** 사진첩에 음식 사진이 수백 장 쌓여 있어도
"저번에 갔던 그 집 어디였지"를 해결해주지 못한다.

**기록 앱은 입력이 귀찮아서 죽는다.** 매번 가게를 검색하고 평점을 매기고 메모를
쓰는 일을 계속할 사람은 거의 없다.

---

## 3. 해결 방식

**① 입력 부담을 0에 가깝게**
사용자는 평소처럼 사진만 찍는다. 앱이 사진첩에서 음식 사진을 찾아 EXIF 좌표로
장소를 추정해 카드로 띄운다. 사용자는 확인하거나 넘기기만 한다.

**② 신뢰는 관계에서**
전체 공개가 아니라 클럽(친구 그룹) 안에서만 공유된다. 광고가 낄 자리가 없고
평가자가 누구인지 안다.

**③ 쌓인 기록이 나를 돕는다**
"지금 이 근처, 친구가 또 간다고 한 곳"이 이 앱의 존재 이유다.
기록하는 동기와 사용하는 동기가 서로를 먹여살린다.

## 4. 차별점

| | 네이버·카카오 | 인스타 | 개인 기록 앱 | **우맛공** |
|---|---|---|---|---|
| 신뢰도 | 광고 혼재 | 협찬 혼재 | 본인만 | **아는 사람만** |
| 입력 부담 | 리뷰 작성 | 게시물 작성 | 수동 입력 | **사진 자동 인식** |
| 위치 기반 탐색 | 있음 | 없음 | 약함 | **친구 데이터 기반** |

**주 사용자:** 20~30대. 외식이 잦고 음식 사진을 찍으며 친한 친구 그룹이 있는 사람
**클럽 규모:** 5~15명. 이보다 크면 신뢰가 희석되고, 작으면 데이터 밀도가 안 나온다

## 5. 핵심 시나리오

### S1. 첫 실행 — 이미 있던 기록을 되찾는다

**이 앱의 성패가 여기서 갈린다.** "이제부터 기록하세요"가 아니라
"이미 이만큼 있었네요"로 시작해야 한다.

1. 사진첩 접근 요청 — 최근 1년, 음식 사진만 찾겠다고 고지
2. 온디바이스로 음식 사진을 걸러내고 EXIF 좌표로 장소 추정
3. "38곳을 찾았어요" — 지도에 핀이 찍힌다
4. 스와이프로 빠르게 확인. 맞으면 남기고 아니면 넘긴다
5. 3분 만에 나만의 지도 완성

**예외**
- 위치 정보 없는 사진 → "위치 미정" 묶음으로 분리. 온보딩에서 붙잡지 않는다
- 음식 사진 10장 미만 → 온보딩 건너뛰고 "지금 어디 계세요?"로 첫 기록 유도

### S2. 기록

1. 밥 먹고 사진을 찍는다 (앱을 열지 않음)
2. 나중에 앱을 열면 새 사진이 카드로 대기 중
3. 장소가 자동 추정되어 있다. 틀리면 후보에서 고르거나 검색
4. 평가 3단계 중 하나 — **또 갈래 / 괜찮아 / 한 번은**
5. 한 줄 메모는 선택

**위치 확정 우선순위**
EXIF 좌표 → 주변 후보 자동 제시 / 좌표 없음 → 검색 또는 "지금 내 위치로 등록" /
둘 다 아님 → 지도에서 직접 찍기

### S3. 탐색 — 존재 이유

1. 외출 중 밥 먹을 곳을 정해야 한다
2. 「내 근처 맛집」을 누른다
3. GPS 기준 반경 내에서 클럽 친구가 「또 갈래」를 누른 곳이 뜬다
4. 누가 언제 갔는지, 어떤 사진을 찍었는지, 한 줄 평이 보인다

### S4. 클럽

초대 링크를 카톡으로 보내면 끝. 계정 검색·친구 요청·수락 절차를 만들지 않는다.
합류 즉시 S1 온보딩이 돌아 그 친구의 기록도 지도에 합쳐진다.

## 7. 데이터 모델

```
users          id, name, avatar, created_at

clubs          id, name, color, created_by, invite_code,
               plan, plan_expires_at
club_members   club_id, user_id, joined_at

places         id, name, address, coordinate, category,
               source (API | USER), external_id, created_by, club_id,
               category_tags[]

visits         id, user_id, place_id, club_id,
               rating (AGAIN | OKAY | NOPE),
               memo, visited_at, visibility (CLUB | PRIVATE)

visit_photos   id, visit_id, thumb_url, taken_at,
               exif_coordinate, tags[], tag_source
```

**설계 노트**

- `places`는 카카오 장소 ID를 외래키로 물려 중복을 막는다. 같은 가게를 친구 셋이
  기록해도 하나로 모인다. 동시에 이 캐싱이 API 비용을 줄이는 핵심 장치다
- `source=USER`인 커스텀 장소는 해당 클럽 안에서만 후보로 노출한다
- `visits`가 사실상 이 앱의 전부다. 사진은 부속물
- 평가는 3단계 enum. 숫자 척도로 바꾸지 않는다
- 화면 라벨: `AGAIN` 또 갈래 / `OKAY` 괜찮아 / `NOPE` 한 번은
- 사진 원본은 서버에 올리지 않는다. 썸네일만
- `tags`는 검색 인덱스 용도다. 화면에 확정 정보처럼 노출하지 않는다

## 8. 설계 원칙

**입력을 3초 안에 끝낸다.**
평가를 3단계로 제한하는 이유다. 10점 척도는 고민하게 만들고, 고민하면 안 쓴다.
사람마다 기준이 달라 내 7점과 친구 7점이 다른 의미가 된다. "또 갈래"는 기준이 명확하다.

**혼자서도 완결되어야 한다.**
친구가 없으면 빈 화면인 앱은 죽는다. 나만의 지도를 채우는 것만으로 쓸모 있어야 하고,
클럽은 그 위에 얹는다.

**앱이 먼저 말을 건다.**
사용자가 "기록해야지" 하고 앱을 여는 일은 없다. 새 음식 사진이 감지되면
앱이 카드를 준비해두고 알린다.

**수집욕을 자극한다.**
경쟁자는 구글 지도가 아니라 스티커 앨범이다. 핀이 늘어나는 지도, 채워지는 지역,
방문 수 카운터가 기능만큼 중요하다.

**태그는 틀려도 되지만 지어내면 안 된다.**
자동 태그는 검색 인덱스일 뿐 확정 정보가 아니다. 결과에 관련 없는 항목이 몇 개
섞이는 것은 허용한다. 사진이 함께 보이므로 사용자가 눈으로 걸러낸다.
반대로 확신도가 낮을 때 억지로 태그를 붙이면 검색 전체의 신뢰가 무너진다.

## 9. 수익 모델

> **출시 시점에는 과금을 켜지 않는다.** 이 장은 나중에 과금을 붙일 때 구조를
> 바꾸지 않기 위한 사전 설계다. 초기 목표는 수익이 아니라 실사용자 확보다.

### 원칙

**앱을 더 많이 쓰는 사람이 낸다.** 과금이 사용을 억제하면 안 된다.

**광고를 넣지 않는다.** 유일한 차별점이 "광고 없는 진짜 리뷰"다.
가게 홍보가 들어오는 순간 존재 이유가 사라진다.

**데이터를 팔지 않는다.** 친구끼리 믿고 쓰는 앱이 데이터를 판다는 사실이 알려지면
그날로 끝난다.

**유입 수수료를 받지 않는다.** "추천이 돈 때문 아니냐"는 의심을 부른다.

### 과금 단위 — 클럽

개인 구독이 아니라 **클럽장이 결제하고 멤버 전원이 혜택을 받는** 구조.
1인당 체감 부담이 낮고, 친구 여럿이 함께 쓰는 중이라 해지가 어렵다.

| 항목 | 무료 | 유료 |
|---|---|---|
| **클럽 정원** | **8명** | 30명 |
| 과거 사진 스캔 | 최근 1년 | 전체 |
| 사진 보관 화질 | 압축 썸네일 | 원본 |
| 클럽 개수 | 1개 | 3개 |
| 통계·결산 | 기본 | 히트맵, 지역 정복도, 결산 카드 |

**가격(가설):** 클럽당 월 4,900원

**정원 8명의 근거:** 5명은 「주변」 기능이 작동할 데이터 임계점에 못 미친다.
가치를 체감하기 전에 결제 화면을 만나면 결제도 안 하고 앱도 떠난다.
8명이면 근처 추천이 실제로 뜨기 시작하고, 그 상태에서 9번째 친구를 초대하려다
벽을 만나는 것이 가장 자연스러운 전환 지점이다.

**정원 초과 시:** 기존 멤버 접근을 막지 않는다. **초대만 차단**한다.

### 설계에 미리 반영할 것

- `clubs`에 `plan`, `plan_expires_at`
- 무료 제한값(정원 8, 스캔 1년, 클럽 1개)을 **하드코딩하지 말고 설정값으로 분리**
- 결제 연동 자리만 남기고 구현은 이후

## 10. 리스크

| 리스크 | 대응 |
|---|---|
| **사진첩 전체 접근 거부** | 첫 요청은 제한적 접근. 가치 체감 후 전체 접근 제안. 온디바이스 처리를 명확히 고지 |
| **클럽에 데이터가 없어 빈 화면** | S1 온보딩으로 첫날 30~50곳 확보. 친구 3명이면 100곳 이상 |
| **좌표 → 가게 매칭 실패** | 건물 내부 GPS 오차, 상가 밀집. 후보 목록 제시 + 사용자 선택을 기본 흐름으로 |
| **위치 정보 없는 과거 사진** | 별도 묶음 분리. "현재 위치" 대안은 실시간 기록에만 유효하므로 검색·지도 지정으로 유도 |
| **한식 태그 정확도** | 아래 10.1 참조 |
| **음식 사진을 안 찍는 사용자** | R-10(사진 없이 기록)으로 대체 경로 |
| **사진 저장 비용** | 원본 미저장. 썸네일만 |

### 10.1 태그 정확도 보완

**기본 — 온디바이스.** iOS Vision, Android ML Kit. 서버 비용 0, 사진을 외부로 보내지 않음.

**한계.** 기본 모델은 서양 음식에 강하고 한식에 약하다. 파스타·스테이크는 잘 잡히지만
돈까스·국밥·제육볶음은 뭉뚱그린 영문 라벨로 나온다.

**3단 보완**
1. **한국어 매핑 사전** — 영문 라벨을 한식 어휘로 변환. 초기 100~200개, 별도 자산으로 관리
2. **가게 업종 결합** — 카카오가 주는 업종 정보를 태그에 합친다. 사진 분석보다 정확할 때가 많다
3. **친구 데이터 재사용** — 같은 가게를 친구가 기록했으면 그 태그를 가져온다

**대비책 — 서버 분석 전환**
위 3단으로도 부족하면 서버 측 분석으로 전환하되, 다음을 전제로 한다.
썸네일만 전송 / 분석 후 즉시 폐기 / 사용자가 끌 수 있게 / **온보딩 대량 스캔은
온디바이스 유지**(비용 방어).

전환 기준: 온디바이스 태그가 붙는 사진 비율이 **6할 미만**일 때.
